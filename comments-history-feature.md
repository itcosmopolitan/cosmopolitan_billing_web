# Feature: Comments & History (Activity Drawer)

## 0. Summary

Add a unified **Comments & History** side drawer to every record-level tab in
**Purchases** (Purchase Bills, Purchase Orders, GRN, Vendor Returns) and
**Sales** (Invoices, Sales Orders, Quotations, Credit Notes / Returns).

The drawer shows a single chronological timeline mixing:
- **System history entries** — auto-logged, immutable, generated by the backend
  whenever a tracked field/event changes on a record.
- **User comments** — free-text notes added manually by staff/admins,
  editable/deletable by the author (within a time window) or by Admin.

Access to viewing and posting comments is **role-based** and configurable in
Settings → Roles & Permissions. System history visibility can be gated
separately from comment visibility.

Payments tabs (Sales Payments, Purchase Payments) do **NOT** get their own
drawer. Payment events are logged onto the parent record's timeline only
(see §1.4).

This doc is split into three implementable layers: Database → Backend API →
Frontend. Each layer has explicit file/module targets, schemas, and contracts
so it can be implemented independently and in order.

---

## 1. Scope & Behavior Rules

### 1.1 Supported record types (polymorphic target)

| record_type        | Source tab                          | Module     |
|---------------------|--------------------------------------|------------|
| `purchase_bill`     | Purchases → Purchase Bills           | purchases  |
| `purchase_order`    | Purchases → Purchase Orders          | purchases  |
| `grn`                | Purchases → GRN (Receipts)           | purchases  |
| `vendor_return`      | Purchases → Vendor Returns           | purchases  |
| `sales_invoice`      | Sales → Invoices                     | sales      |
| `sales_order`        | Sales → Sales Orders                 | sales      |
| `quotation`           | Sales → Quotations                  | sales      |
| `credit_note`         | Sales → Credit Notes / Returns      | sales      |

`record_type` + `record_id` together form the polymorphic key used by both
`activity_comments` and `activity_history` tables (see §2).

### 1.2 Excluded record types

- `purchase_payment`, `sales_payment` rows do **not** get a drawer entry
  point in the UI. Their events are written to the **parent** record's
  history (e.g. paying a Purchase Bill writes a `payment_recorded` entry onto
  that bill's `activity_history`, not onto a separate payment-level thread).

### 1.3 Shell behavior (applies identically to every record_type)

- Icon button rendered in the row-actions area of every list row, next to the
  existing "⋮" menu, for all record types in §1.1.
- Click opens a right-side drawer (slide-in, ~420px desktop / full-width
  mobile) without navigation; underlying list dims but stays mounted.
- Drawer header shows: record number/code, a 1-line summary
  (counterparty name, amount, status badge), close button.
- Drawer has 3 filter tabs: **Timeline** (default, merged) / **Comments** /
  **System only**.
- Scrollable timeline body, newest at bottom (chat-like), auto-scrolled to
  bottom on open.
- Comment composer pinned at drawer bottom — rendered only if the current
  user's role has `comments.add` for that module; otherwise replaced with a
  disabled note ("You don't have permission to comment here").
- A small unread-dot badge on the row icon if there are comments/history
  newer than the user's `last_viewed_at` for that record (see §2.4).

### 1.4 Per-record-type history event catalogue

Each record type auto-logs a fixed set of `event_type` values (see §2.2 for
the enum). Backend modules MUST emit exactly these — do not invent ad hoc
strings.

**purchase_bill**
`created`, `item_changed`, `status_changed`, `payment_recorded`,
`due_date_changed`, `amount_changed`, `grn_linked`, `voided`

**purchase_order**
`created`, `approved`, `item_changed`, `converted`, `cancelled`

**grn**
`created`, `qty_received_recorded`, `discrepancy_flagged`, `verified`,
`linked_to_source`

**vendor_return**
`created`, `voided`, `unvoided`, `reason_set` (reserved, no current route),
`refund_status_changed` (reserved, no current route),
`credit_applied` (reserved, no current route)

Note: `cancelled` may still be emitted for bulk-delete/audit cleanup flows;
it is operational and outside the six business-catalogue events above.

**sales_invoice**
`created`, `item_changed`, `status_changed`, `payment_recorded`,
`return_linked`, `voided`

**sales_order**
`created`, `confirmed`, `item_changed`, `converted`, `cancelled`

**quotation**
`created`, `sent`, `revised`, `accepted`, `rejected`, `expired`, `converted`

**credit_note**
`created`, `reason_set`, `refund_issued`, `stock_returned`

Cross-record conversion events (`converted`) MUST store
`metadata.target_record_type` and `metadata.target_record_id` so the
frontend can render a clickable cross-link ("Converted to PUR-2026-0403")
without a second query.

### 1.5 Permission model

New permission keys (see §2.3 for table, §3.5 for enforcement):

| Key                    | Effect                                                         |
|-------------------------|------------------------------------------------------------------|
| `history.view`          | Can open drawer and see system history entries                |
| `comments.view`         | Can open drawer and see comments                               |
| `comments.add`          | Can post new comments                                          |
| `comments.edit_own`     | Can edit/delete own comments within `COMMENT_EDIT_WINDOW_MIN`  |
| `comments.delete_any`   | Can delete/edit any comment (Admin override)                  |

Default role presets (seed data, see §2.6):
- `super_admin`, `admin` → all 5 permissions = true
- `staff` → `history.view`=true, `comments.view`=true, `comments.add`=true,
  `comments.edit_own`=true, `comments.delete_any`=false

If a role has neither `history.view` nor `comments.view`, the drawer icon is
hidden entirely for that role (not just disabled).

## 2. Database Layer

Target: PostgreSQL. Adjust types if project uses MySQL/SQLite — call out
`UUID`, `JSONB`, `TIMESTAMPTZ` as the only Postgres-specific types used.

### 2.1 Migration file

Create: `migrations/<timestamp>_create_activity_tables.sql`
(or the ORM-equivalent migration file matching the project's existing
migration tool — Prisma/TypeORM/Knex/Sequelize. Mirror this DDL exactly.)

```sql
-- Enum for polymorphic record type
CREATE TYPE activity_record_type AS ENUM (
  'purchase_bill',
  'purchase_order',
  'grn',
  'vendor_return',
  'sales_invoice',
  'sales_order',
  'quotation',
  'credit_note'
);

-- ============================
-- activity_history (system log)
-- ============================
CREATE TABLE activity_history (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  branch_id       UUID REFERENCES branches(id) ON DELETE SET NULL,
  record_type     activity_record_type NOT NULL,
  record_id       UUID NOT NULL,
  event_type      VARCHAR(64) NOT NULL,         -- e.g. 'status_changed'
  actor_id        UUID REFERENCES users(id) ON DELETE SET NULL,
  actor_label     VARCHAR(64) NOT NULL DEFAULT 'System', -- denormalized, survives user deletion
  description     TEXT NOT NULL,                 -- pre-rendered human string, e.g.
                                                    -- "Status changed: Pending -> Partial"
  metadata        JSONB NOT NULL DEFAULT '{}',   -- old/new values, linked record ids, etc.
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_activity_history_record
  ON activity_history (org_id, record_type, record_id, created_at DESC);

-- ============================
-- activity_comments (user notes)
-- ============================
CREATE TABLE activity_comments (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  branch_id       UUID REFERENCES branches(id) ON DELETE SET NULL,
  record_type     activity_record_type NOT NULL,
  record_id       UUID NOT NULL,
  author_id       UUID NOT NULL REFERENCES users(id) ON DELETE SET NULL,
  body            TEXT NOT NULL,
  is_pinned       BOOLEAN NOT NULL DEFAULT false,
  edited_at       TIMESTAMPTZ,
  deleted_at      TIMESTAMPTZ,                   -- soft delete; keep row for audit
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_activity_comments_record
  ON activity_comments (org_id, record_type, record_id, created_at DESC);

-- ============================
-- activity_views (per-user last-seen, drives unread badge)
-- ============================
CREATE TABLE activity_views (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  record_type     activity_record_type NOT NULL,
  record_id       UUID NOT NULL,
  last_viewed_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (user_id, record_type, record_id)
);

-- ============================
-- role_permissions additions (extend existing table; do not recreate
-- if a role_permissions table already exists in the project — just
-- add rows via seed, see 2.6)
-- ============================
-- Assumes existing structure: role_permissions(role_id, permission_key, allowed BOOLEAN)
-- New permission_key values to insert per role:
--   history.view, comments.view, comments.add, comments.edit_own, comments.delete_any
```

### 2.2 Notes on schema decisions

- `record_id` is a plain `UUID`, not a foreign key — because it polymorphically
  points to 8 different tables. Application-layer integrity only (validate
  existence in the service layer before insert, see §3.2).
- `activity_history.description` is **pre-rendered** server-side at write
  time (not computed at read time from `metadata`). This keeps history
  immutable in meaning even if later code changes how a given event type is
  phrased. `metadata` is kept alongside for programmatic use (cross-links,
  diffs) but the rendered string is canonical.
- `activity_comments` uses soft delete (`deleted_at`) so deleted comments
  remain in the audit trail for compliance, just hidden from normal views.
  Hard-delete is never exposed via API.
- `is_pinned` is included for the "pin important comment" nice-to-have from
  the design doc; safe to ignore in v1 if not building that yet, but keep
  the column so no migration is needed later.

### 2.3 Permission seed

Insert file: `seeds/activity_permissions_seed.sql`

```sql
INSERT INTO permissions (key, label, module) VALUES
  ('history.view', 'View system history', 'activity'),
  ('comments.view', 'View comments', 'activity'),
  ('comments.add', 'Add comments', 'activity'),
  ('comments.edit_own', 'Edit/delete own comments', 'activity'),
  ('comments.delete_any', 'Delete any comment (admin override)', 'activity')
ON CONFLICT (key) DO NOTHING;

-- super_admin & admin: all true
INSERT INTO role_permissions (role_id, permission_key, allowed)
SELECT r.id, p.key, true
FROM roles r, permissions p
WHERE r.slug IN ('super_admin', 'admin')
  AND p.module = 'activity'
ON CONFLICT (role_id, permission_key) DO UPDATE SET allowed = true;

-- staff: all true except delete_any
INSERT INTO role_permissions (role_id, permission_key, allowed)
SELECT r.id, p.key,
  CASE WHEN p.key = 'comments.delete_any' THEN false ELSE true END
FROM roles r, permissions p
WHERE r.slug = 'staff'
  AND p.module = 'activity'
ON CONFLICT (role_id, permission_key) DO UPDATE SET allowed = EXCLUDED.allowed;
```

> If the project's roles/permissions tables use a different shape (e.g. a
> single JSON column on `roles`), adapt the seed accordingly but preserve
> the 5 permission keys verbatim — the frontend and backend middleware in
> this doc reference them by exact string.

### 2.4 Config constant

Add to backend config (e.g. `config/constants.ts` or `.env`):

```
COMMENT_EDIT_WINDOW_MIN=15
```

Used to compute whether `comments.edit_own` still applies to a given
comment (`now() - comment.created_at <= 15 minutes`), independent of
`comments.delete_any` which is always unrestricted by time.

## 3. Backend API Layer

Framework-agnostic contracts below; written as REST. Adapt verbs/paths to
existing API conventions (e.g. if project uses `/api/v1/...` prefix, nest
under that).

### 3.1 Routes

```
GET    /api/activity/:recordType/:recordId
       -> merged, paginated timeline (history + comments)

POST   /api/activity/:recordType/:recordId/comments
       -> create a comment

PATCH  /api/activity/comments/:commentId
       -> edit a comment body

DELETE /api/activity/comments/:commentId
       -> soft-delete a comment

POST   /api/activity/:recordType/:recordId/mark-viewed
       -> upsert activity_views.last_viewed_at = now()

GET    /api/activity/unread-summary?recordType=&recordIds[]=
       -> bulk endpoint: returns { recordId: boolean } unread map for a
          page of list rows (used to render the row-level unread dot
          without N+1 requests)
```

`:recordType` must be one of the 8 enum values in §1.1 — validate and 400 on
anything else (in particular, explicitly 400 on `purchase_payment` /
`sales_payment` to make the exclusion in §1.2 enforced server-side, not just
hidden client-side).

### 3.2 GET /api/activity/:recordType/:recordId

**Auth:** requires `history.view` OR `comments.view` (at least one; response
content is filtered per-permission, see below).

**Query params:** `?filter=all|comments|history` (default `all`),
`?cursor=&limit=50`

**Response:**
```json
{
  "record": { "type": "purchase_bill", "id": "uuid", "summary": "PUR-2026-0402 · Hari · ₹10" },
  "items": [
    {
      "kind": "history",
      "id": "uuid",
      "event_type": "status_changed",
      "description": "Status changed: Pending -> Partial",
      "actor_label": "System",
      "metadata": { "from": "pending", "to": "partial" },
      "created_at": "2026-06-13T14:10:00Z"
    },
    {
      "kind": "comment",
      "id": "uuid",
      "body": "Vendor asked for partial payment this week",
      "author": { "id": "uuid", "name": "Suresh Anand" },
      "is_pinned": false,
      "edited_at": null,
      "can_edit": true,
      "can_delete": true,
      "created_at": "2026-06-13T10:35:00Z"
    }
  ],
  "next_cursor": null
}
```

Server logic:
1. Resolve caller's permissions for the module owning `recordType`.
2. If only `history.view` is granted, fetch from `activity_history` alone
   (ignore comments table even if `filter=all`).
3. If only `comments.view` granted, mirror inverse.
4. If both granted, union both tables, sort by `created_at` ascending,
   paginate by cursor.
5. Per comment row, compute `can_edit` / `can_delete`:
   - `can_delete` = `comments.delete_any` OR (`comments.edit_own` AND
     `author_id == caller.id` AND within `COMMENT_EDIT_WINDOW_MIN`)
   - `can_edit` = same rule as `can_delete` (no separate edit-only rule in
     v1)
6. Never return soft-deleted comments (`deleted_at IS NULL` filter), except
   to admins with `comments.delete_any` who may see a
   `"[deleted by admin]"` placeholder row instead of omitting it entirely —
   implementer's choice, but pick one and apply consistently.

### 3.3 POST /api/activity/:recordType/:recordId/comments

**Auth:** requires `comments.add`.
**Body:** `{ "body": "string, 1-2000 chars", "is_pinned": false }`
**Validation:** body required, trimmed length > 0, max 2000 chars.
**Effect:** insert row; do NOT also write to `activity_history` — comments
and history are separate tables, never duplicate a comment as a history
entry.
**Response:** the created comment object (same shape as in §3.2 `items[]`).

### 3.4 PATCH / DELETE /api/activity/comments/:commentId

**Auth:** PATCH requires `can_edit` per the rule in §3.2 step 5; DELETE
requires `can_delete`. Re-derive server-side per request — never trust a
client-sent `can_edit` flag.
**PATCH body:** `{ "body": "new text" }` → sets `edited_at = now()`.
**DELETE:** sets `deleted_at = now()`, body untouched (kept for audit
export even though hidden from normal reads).
**Both:** 403 if rule fails, 404 if comment not found or already deleted.

### 3.5 Emitting history entries (internal, not a public route)

### 3.6 Unread summary endpoint

```
GET /api/activity/unread-summary?recordType=purchase_bill&recordIds=id1,id2,id3
```
Returns:
```json
{ "id1": true, "id2": false, "id3": true }
```
Logic per id: `true` if `MAX(activity_history.created_at, activity_comments.created_at)
for that record > activity_views.last_viewed_at` (or no view row exists yet
→ true, i.e. unread by default if never opened... EXCEPT for the record's
own creator who should not see their own creation as "unread" — initialize
an `activity_views` row at record-creation time for the creator to avoid
this false positive).

Used by the list page to batch-fetch unread dots for all visible rows in
one call instead of one call per row.

## 4. Frontend Layer

Stack assumed: React + TypeScript (adjust import paths if project differs;
component boundaries below are still correct as a checklist of "what file
does what" regardless of framework).

### 4.1 New components

```
src/components/activity/
  ActivityDrawer.tsx        — the drawer shell (header, tabs, body, composer)
  ActivityTimeline.tsx      — renders the merged list of HistoryEntry | CommentEntry
  HistoryRow.tsx            — single immutable system-log row (dot + text)
  CommentBubble.tsx          — single comment (avatar, body, edit/delete actions)
  CommentComposer.tsx        — textarea + send button, permission-gated
  ActivityIconButton.tsx     — the row-level trigger icon with unread dot
  useActivity.ts              — data hook: fetch, paginate, optimistic post/edit/delete
  activityPermissions.ts      — pure functions wrapping the 5 permission keys
```

### 4.2 `ActivityIconButton`

Props: `{ recordType: ActivityRecordType; recordId: string; hasUnread: boolean }`

Renders nothing (returns `null`) if caller lacks both `history.view` and
`comments.view` (check via existing auth/permissions context — do not make
a network call just to decide visibility; permissions should already be in
the client's session/role context).

On click: opens `ActivityDrawer` (likely via a global drawer/portal
context already used elsewhere in the app for side panels — reuse it,
don't build a second portal mechanism).

Fires `POST /mark-viewed` on drawer open (fire-and-forget) so the unread dot
clears.

### 4.3 `ActivityDrawer`

Props: `{ recordType, recordId, summary: string, onClose: () => void }`

- Header: summary text + close button.
- Tabs: Timeline / Comments / System only — local state, refilters the
  already-fetched list client-side (no refetch on tab switch since
  `filter=all` already pulled everything; only refetch if you choose to
  paginate per-filter, which is not required for v1 given expected volume
  per record is low, typically <50 entries).
- Body: `<ActivityTimeline items={items} />`, scrolled to bottom on mount.
- Footer: `<CommentComposer />` if `comments.add` else permission note.

### 4.4 `ActivityTimeline` / `HistoryRow` / `CommentBubble`

- `ActivityTimeline` maps `items[]` (already sorted ascending by backend)
  to `HistoryRow` for `kind: 'history'` and `CommentBubble` for
  `kind: 'comment'`, connected by a vertical line (see the earlier mockup
  in this conversation for the exact visual — gray dot for history, filled
  circle/bubble for comments).
- `HistoryRow`: no interactive elements at all. Just dot + description +
  `actor_label · relative timestamp`.
- `CommentBubble`: shows body, author, timestamp (+ "edited" tag if
  `edited_at` set). Shows Edit/Delete inline text actions only if
  `item.can_edit` / `item.can_delete` from the API response — do not
  recompute permission logic in the frontend beyond reading those two
  booleans.
- Edit: turns body into an inline textarea, Save calls `PATCH`, optimistic
  update, rollback on error.
- Delete: confirm (simple browser `confirm()` or existing app confirm
  modal pattern) → `DELETE`, optimistically remove from list.

### 4.5 `CommentComposer`

- Controlled textarea, 1-2000 char client-side guard mirroring backend.
- Send button disabled while empty or while a request is in flight.
- On submit: `POST` comment, optimistically append to timeline, clear
  textarea, scroll to bottom.
- Enter = newline, Cmd/Ctrl+Enter = send (standard chat composer pattern).

### 4.7 Cross-link rendering

When a `HistoryRow`'s `event_type === 'converted'` (or `return_linked` /
`grn_linked`), render the description with the target record number as a
clickable link using `metadata.target_record_type` /
`metadata.target_record_id`, navigating to (or opening the drawer for) that
target record. Exact navigation target depends on existing routing
conventions in the app — link to that record's detail view/row, not its
drawer directly, unless the app has no detail view per record (in which
case open that record's own `ActivityDrawer` instead).

### 4.8 Mobile

Drawer becomes full-screen instead of 420px side panel below a breakpoint
(reuse whatever breakpoint the project's existing modals/drawers use).

## 5. Implementation Order (suggested)

1. **DB**: run migration (§2.1), run permission seed (§2.3).
2. **Backend**: implement `logHistory` helper (§3.5) and wire into
   `purchase_bill` and `sales_invoice` services first (highest-value tabs

   query before building more.

   types.
4. **Frontend**: build `ActivityDrawer` + children against the
   `purchase_bill` / `sales_invoice` endpoints; ship icon on those two
   tabs only.
5. **Backend**: wire `logHistory` into remaining 6 record types (§3.5
   table) and confirm event catalogue (§1.4) per type.
6. **Frontend**: wire `ActivityIconButton` into remaining 6 tabs (§4.6) —
   no new components needed, just prop changes per tab.
7. **Polish**: unread badges (§3.6, §4.6), pinning, mobile breakpoint.
